# Parte 5: Desafio de IA

## Questão 8

O endpoint `POST /api/v1/agent/query` recebe uma pergunta, normaliza texto e identifica uma intenção por regras determinísticas. O resultado do parsing não é uma consulta direta: ele é uma chamada estruturada com nome de ferramenta e argumentos validados.

Por exemplo, “quais produtos estão com estoque abaixo de 10 unidades?” produz:

```json
{
  "name": "find_low_stock",
  "arguments": {
    "max_quantity": 10
  }
}
```

Um registro permite somente a ferramenta `find_low_stock`. O executor despacha a chamada para a camada de serviço, que consulta o repository. Perguntas não reconhecidas retornam `422` antes de qualquer acesso aos dados.

Essa separação é intencional: parser, autorização de ferramentas e execução têm responsabilidades diferentes. Ainda é uma solução pequena, mas permite substituir o parser por outro mecanismo sem entregar acesso irrestrito ao banco.

A resposta expõe a tradução e o resultado:

```json
{
  "tool_call": {
    "name": "find_low_stock",
    "arguments": {
      "max_quantity": 10
    }
  },
  "result": []
}
```

## Questão 9

### Evolução para um LLM

Eu manteria as ferramentas como contratos independentes do modelo. Um LLM poderia sugerir a mesma estrutura de `tool_call`, mas nome, argumentos, autenticação e permissões continuariam validados pela aplicação. O modelo não receberia credenciais de banco nem produziria SQL executado diretamente.

Uma ferramenta de leitura poderia ter contrato semelhante a:

```json
{
    "name": "find_low_stock",
  "description": "Consulta produtos abaixo de um limite de estoque",
  "parameters": {
    "type": "object",
    "properties": {
      "max_quantity": {
        "type": "integer",
        "minimum": 0
      }
    },
    "required": ["max_quantity"],
    "additionalProperties": false
  }
}
```

Eu começaria por ferramentas de leitura. Uma ação como criar pedido teria contrato próprio, autenticação do usuário, idempotency key e regras de negócio executadas pelo serviço de Pedidos — nunca pelo modelo.

### MCP

MCP pode ser usado como fronteira padronizada para expor essas ferramentas a clientes/agentes diferentes. Um servidor MCP validaria os argumentos e chamaria as APIs dos serviços donos dos dados. Eu o adotaria se houvesse ganho real de interoperabilidade; para um único consumidor interno, uma API/tool registry simples pode ser suficiente.

### Guardrails

Eu separaria leitura de escrita e classificaria ferramentas por risco. Operações destrutivas ou financeiras exigiriam autorização, confirmação explícita e auditoria. Também validaria schema de entrada e saída, limites e ownership do recurso independentemente do que o modelo produzir.

Quando a pergunta fosse ambígua, o agente deveria pedir esclarecimento em vez de escolher silenciosamente. Quando a fonte de dados estivesse indisponível, a resposta deveria identificar a falha; o modelo não pode completar o valor por plausibilidade.

### Custo, latência e observabilidade

Eu monitoraria latência total, tempo do provedor, tool calls, erros de validação, retries e custo por interação. Prompts e respostas exigem redaction e política de retenção porque podem conter dados do ERP.

Cache pode ajudar em consultas de leitura estáveis, mas precisa respeitar usuário e permissões. Timeout, circuit breaker e fallback determinístico preservariam funções básicas quando o modelo estivesse indisponível. Antes de trocar de provedor ou modelo, eu mediria qualidade das interpretações e não apenas custo por token.
