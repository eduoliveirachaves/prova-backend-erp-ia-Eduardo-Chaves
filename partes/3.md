# Parte 3: API RESTful

O modelo `Product` possui `id`, `name`, `price`, `stock_quantity`, `created_at` e `updated_at`. Pydantic rejeita nome vazio ou somente numérico, preço negativo e estoque negativo. O PostgreSQL repete as garantias numéricas com constraints, porque a integridade não deve depender apenas de uma entrada HTTP específica.

## Persistência

Escolhi SQLAlchemy principalmente por familiaridade e pela maturidade do ecossistema. Para um CRUD relacional deste porte, ele reduz código repetitivo sem esconder completamente consultas e transações. A integração com Alembic também mantém a evolução do schema no mesmo ecossistema.

Eu não considero o ORM obrigatório para toda consulta. Em operações específicas, nas quais o SQL gerado ou o volume se tornasse um problema, usaria SQLAlchemy Core ou SQL explícito após medir o gargalo. Nesta implementação, o driver asyncpg evita bloquear o event loop durante I/O com o PostgreSQL.

## Contrato HTTP

As rotas autenticadas oferecem CRUD, paginação e filtros por nome, faixa de preço e estoque baixo. A API usa schemas diferentes para entrada, atualização, leitura e listagem, evitando expor o modelo persistido diretamente.

O update atual usa `PUT` e exige a representação editável completa do produto. Se o requisito passasse a incluir atualização parcial, eu adicionaria `PATCH` com um schema cujos campos fossem opcionais, em vez de mudar silenciosamente a semântica do `PUT`.

## Autenticação

O login valida o hash Argon2 e emite um JWT de curta duração. As rotas protegidas validam assinatura, expiração, subject e situação ativa do usuário.

Isso atende ao escopo da prova. Em um ambiente maior, autorização por perfil, rotação de chaves, audiência/emissor e estratégia de renovação ou revogação dependeriam dos requisitos de segurança; não foram simulados sem necessidade.

## Cache

O `GET /api/v1/products/{id}` usa cache-aside com chave versionada e TTL configurável. Em um miss, consulta PostgreSQL e preenche Redis. Create, update e delete invalidam a chave depois do commit. Se Redis falhar, a resposta segue pelo banco e a falha é registrada.

Aceito que, se uma invalidação falhar, o dado possa permanecer desatualizado até o TTL. Por isso o cache é uma otimização de consulta, não a fonte usada para reservar ou baixar estoque; decisões transacionais sempre consultariam PostgreSQL dentro da transação.

## Processamento em background

Create e update com estoque abaixo do limite enfileiram um job ARQ. O worker lê novamente o produto no PostgreSQL antes de agir, evitando confiar no valor antigo recebido pela fila. O identificador do alerta impede duplicação para o mesmo estado observado.

Para esta prova, o alerta é best effort: uma indisponibilidade da fila é registrada, mas não desfaz um produto já confirmado. Se a perda do alerta causasse impacto financeiro ou operacional crítico, eu revisaria as garantias de entrega e recuperação antes de manter esse desenho.
