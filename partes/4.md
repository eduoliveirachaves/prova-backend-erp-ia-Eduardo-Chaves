# Parte 4: Docker, Orquestração e Entrega

O Dockerfile possui estágios separados para dependências de produção, verificações de qualidade e runtime. O estágio final recebe apenas o ambiente virtual de produção, código, migrações, configuração do Alembic e entrypoint. Pytest, Ruff, mypy e os próprios testes permanecem no estágio `test`.

O Compose sobe quatro serviços da aplicação:

- `app`: migra, executa o seed e inicia Uvicorn;
- `postgres`: persistência transacional;
- `redis`: cache e backend do ARQ;
- `worker`: processamento de alerta de estoque baixo.

PostgreSQL e Redis ficam acessíveis apenas na rede interna do Compose, porque o host não precisa conversar diretamente com eles para usar a API. Isso também evita colisões desnecessárias com instalações locais. A porta da API é configurável por `APP_PORT`, mantendo `8000` como padrão.

Healthchecks do PostgreSQL e Redis impedem que a aplicação seja iniciada antes das dependências básicas. A API possui liveness e readiness; o worker só começa depois que a API e o Redis estão disponíveis.

O fluxo normal é:

```bash
cp .env.example .env
docker compose up --build --wait
```

O entrypoint roda `alembic upgrade head` e um seed idempotente antes do Uvicorn. Eu aceitei essa abordagem por ser simples para uma entrega executada por uma única instância. Em produção, migrações concorrentes durante cada réplica da aplicação exigiriam coordenação ou uma etapa separada de deploy.

As verificações são reproduzíveis sem Python no host:

```bash
docker compose --profile test run --rm --build test
```

Variáveis ficam no `.env`, que é ignorado pelo Git. O arquivo `.env.example` contém apenas valores locais de demonstração; segredos reais não devem ser versionados.
